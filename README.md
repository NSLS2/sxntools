# sxntools

Python tools for the NSLS-II Soft X-ray Nanoprobe beamline. The Pixelator integration is an optional part of the `sxntools` distribution; importing `sxntools` does not import its acquisition dependencies.

## Pixelator simulator round trip

Install the optional dependencies in the repository environment and run the hardware-free example:

```sh
uv sync --group dev --extra pixelator
uv run --extra pixelator python examples/pixelator_roundtrip.py
```

The example binds ZMQ REP/XPUB sockets only on `127.0.0.1`, runs a Bluesky scan against `PixelatorSimulator` with archiving enabled, ingests the **final** HDF5 file through `TiledWriter` into an in-process Tiled server, and downloads the complete file with `raw_export`. It checks the downloaded bytes and a synthetic 3-by-4 dataset containing 0–11. Both controller assets and Tiled storage are temporary. The simulator uses unique directories per scan rather than Pixelator's documented date directory. Tests also cover a successful scan left in the discard directory. `examples/pixelator_request.json` is a **simulator-only** request derived from the public scan example, not a certified request for real hardware.

Import acquisition APIs from their explicit modules: `sxntools.pixelator.protocol` (`ScanRequest`, `ScanResult`), `.client` (`PixelatorClient` and protocol/terminal exceptions), `.flyer` (`PixelatorFlyer`), and `.plans` (`pixelator_scan`). After a successful `scanFinished`, the plan declares the `primary` stream using the completed file URI, then emits one StreamResource and one StreamDatum for the scan file. The `primary/pixelator_file` catalog node remains an opaque **bytes** asset, not an HDF5 array adapter; use `raw_export` to retrieve it. The simulator's `/entry/data/data` dataset is solely an integrity fixture and makes no claim about a real Pixelator array layout.

`PixelatorClient` requires caller-provided request and publisher endpoints plus request, start, and finish timeouts. One client permits one outstanding scan, waits for `scanStarted` and `scanFinished` rather than treating the `['status', 'ok']` acknowledgement as completion, and keeps missing-terminal outcomes uncertain until it observes a terminal event. `abort_scan()` requests abort once and waits for that event; `close()` never sends an abort. The flyer stops an active scan when unstaged. A success result reports the controller's **final** filename; a flag 1 or 2 raises `PixelatorScanAborted` or `PixelatorControllerError` with the reported `ScanResult`. Bluesky's RunEngine wraps a failed completion status in `FailedStatus`, with the specific Pixelator exception as its cause.

`PixelatorFlyer` requires a `path_to_uri` callback mapping `scanFinished.filename` to a `file://` URI that the Tiled server can read. The earlier published `filename` event identifies an in-progress discard file, not necessarily the eventual archive location. There are no default facility endpoints or mount-path assumptions.

[PixelatorControllerSettings](https://gitea.psi.ch/MicroSpectro/Pixelator/wiki/PixelatorControllerSettings) specifies an HDF5 scan file for every scan, initially written under `<selected base>/YYYY-mm-dd/<NeXusDiscardSubDirectory>/`. The selected base is `NeXusBaseDirectory` or `NeXusLocalBaseDirectory` depending on **Save local**. After completion the file moves to the parent date directory if the scan-type archive setting is enabled, or remains in discard otherwise; the documented default is `locked` (archive enabled). [The publisher reference](https://gitea.psi.ch/MicroSpectro/Pixelator/wiki/ZMQ-Publisher-Reference) identifies the final saved/moved filename in `scanFinished`, which is the only filename registered as a Bluesky asset. [Detector configuration](https://gitea.psi.ch/MicroSpectro/Pixelator/wiki/Config_Detector) also permits separate detectors to write their own files; these are not exposed as assets by this flyer. One StreamDatum represents the one whole-file bytes asset, not one datum per live data chunk.

**No live-controller interoperability has been established.** The [request reference](https://gitea.psi.ch/MicroSpectro/Pixelator/wiki/ZMQ-Message-Reference) specifies JSON-list content but not ZMQ frame encoding or scan IDs. The client and simulator assume one UTF-8 JSON-array frame and one isolated client. The wiki does not establish when the HDF5 handle is closed or whether the file is immutable at `scanFinished`: an optional [end-of-scan script can modify it after a scan](https://gitea.psi.ch/MicroSpectro/Pixelator/wiki/HDF5_Thumbnails). Late declaration permits description from a completed file, but an NXstxm assumption alone does not enumerate Pixelator's actual dataset paths, keys, shapes, or index mappings. Per-dataset HDF5 resources would require inspecting that file where it is accessible; the current URI mapper only guarantees Tiled-server visibility. Confirm the controller's ordering, an approved real file, and a catalog-readable mount mapping before any live scan command.
